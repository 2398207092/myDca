## 二、维护规则

### 2.1 分类：按「什么情况下改」分，不按主题分

| 类 | 谁写 | 什么时候改 | 违反时长什么样 |
|---|---|---|---|
| **索引** | 人 | 文档增删 | 导航里有不存在的文件，或文件没登记 |
| **事实** | AI | 增删模块、改数据表、改部署、改「钱」的口径 | `doc-check` 数字对不上 |
| **台账** | AI | 发现问题 / 修好问题 | 一条问题挂 3 个月没人动 |
| **流水** | AI | 每个任务结束 | 超过 30 天没有新增 |
| **流程** | 人 | 测试方法变化 | 脚本改了文档没改，或反过来 |
| **参考** | AI | 算法或口径变化 | 与代码不一致 |
| **归档** | 人 | 文档废弃 | 有现行文档引用它 |

### 2.2 通用操作规则（只有 5 条）

1. **每次任务结束**，往 [04-日志.md](04-日志.md) 末尾追加一条，不超过 5 行。
2. **修了 [03-问题.md](03-问题.md) 里的条目**，同时把它删掉（不要改成「已修复」留着）。
3. **只有这四种情况**才改 01 / 02：新增或删除模块、改数据表、改部署方式、改「钱」的口径。
4. **其余情况不要碰其他文档**。文档数量少但准确，胜过多而失真。
5. **维护不动的文档**，直接移到 `archive/`，并在本页导航里删除该行。宁可少一份，不留假文档。

### 2.3 新增文档：先过三道问

1. **能并入 2.1 里已有的类吗？** 能就并，不新建。
2. **它带来的是「新的变化触发方式」吗？** 例如 05 的触发是「测试方法变化」，此前没有哪份文档负责这件事——所以它独立成篇成立。
3. **新建必须同时做三件事**：登记本页导航并标注类别、编号紧接上一个、在 2.1 补一行维护规则。

> 只做 1、2 不做 3，就是 2026-10-27 那次 `06-UI测试.md` 的事故：文件建了、编号跳了、规则没跟上。

### 2.4 规则怎么自我维持

规则不能自我执行，但可以**自我暴露**——每条规则都要写清「违反时是什么样」，人和 AI 才有判断依据。

1. **短**：5 条通用规则 + 一张分类表。超过一页就没人读。
2. **每条规则绑一个触发点**，不写「要记得」：
   - 改代码 → `bash scripts/doc-check.sh`（事实类）
   - 结束任务 → 写 `04`（流水类）
   - 修问题 → 删 `03`（台账类）
   - 改测试脚本 → 同步 `05`（流程类）
   - 文档增删 → 改本节导航与 2.1（索引类）
3. **季度体检三个问题**（4/1、7/1、10/1、1/1）：
   - 有没有文档不属于 2.1 里的任何一类？
   - 有没有规则从没被触发过？说明是空话，删掉。
   - 有没有「违反的样子」已经出现但没人处理？
4. **索引类目前没有自动检查**：未登记文件、编号跳号，只能靠季度体检发现。要补的话，加进 `doc-check.sh`。

### 2.5 谁能改这套规则

| 对象 | 谁能改 | 约束 |
|---|---|---|
| 2.1–2.4 的规则 | **只有用户** | AI 可以提建议，但必须等用户点头；改完在 `04` 记一条「为什么改」 |
| `AGENTS.md` / `MEMORY.md` | AI 可改，但要先分类 | 「别的 AI 不知道会出事」→ AGENTS；「只有 WorkBuddy 需要」→ MEMORY |
| 单份文档的内容 | AI 按 2.2 / 2.3 自行维护 | 超出 2.2 列举的情况，先问用户 |

> 这条是硬边界：**规则本身不是 AI 的编辑对象**。想加一条规则，先说清「现在的规则哪里不够用」，再由用户决定。

### 为什么这么设计

- **加载机制（2026-10-27 实测）**：`AGENTS.md` 与 `.workbuddy/memory/MEMORY.md` 在会话启动时**自动注入**；`docs/` 需主动 Read。
  所以：规则与红线放 AGENTS（每次都在），项目状态与踩坑放 MEMORY，详细事实放本目录。
  **改 AGENTS / MEMORY 对当前会话无效，下次会话生效。**
- **按「什么时候改」分类**，因为维护动作由触发时机决定，不由内容主题决定。按主题分会出现「一份文档里一半常改、一半从不改」。
- **状态用目录位置表达**：在 `docs/` 根下 = 有效；在 `archive/` = 废弃。不写状态字段。
- **只有 04 是高频写入**（追加 5 行），01/02 一年改几次，03 只减不增。维护成本足够低，才不会烂尾。
