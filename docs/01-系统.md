## 六、四条核心链路

```
A. 净值 → 市值（每天 22:00）
   FundNavScheduler → refreshAllHoldings()
     → incrementalUpdate(code) → fund_nav_records（只写 > maxDateInDb 的记录）
     → applyLatestNav() → holdings.latestPrice / marketValue
     → calculatePredictedDividend() → recalculateHoldingMetrics()

B. 分红 → 事件 → 到账（6:00 / 9:30）
   FundDividendScheduler → scrapeAndSave(code) → fund_dividend_records
     → syncAllEvents() → dividend_events（登记/除息/派发各 1 条）
     → DividendAutoDistributeScheduler（9:30）→ markDistributed()
     → 现金 +amount，或按净值转 reinvest 份额

C. 交易 → 份额/成本/现金（同步）
   TradeAddPage → createTransaction()
     → 写 transactions + 改 shares
     → calculatePredictedDividend → recalculateHoldingMetrics
     → adjustCash(±total) → publishEvent(TransactionChangedEvent)
     → AFTER_COMMIT 监听器补齐分红事件

D. 快照 → 走势图（每月 1/6/11/16/21/26/31 日 23:30）
   HoldingSnapshotScheduler → snapshotAllHoldings()
     → holding_snapshots（每持仓一条，覆盖当天）
     → assetOverviewService.snapshotToday() → asset_snapshots（分类级，含现金）

> **资产分类口径（2026-10-30 用户定）**：5 类 = 现金（含现金手动资产 + **稳定币** USDT/USDC/DAI/TUSD）、红利、美股、黄金、加密资产（**不含稳定币**，即 BTC 等）。实现：`AssetOverviewService.getOverview` 用 `ManualAssetService.getStablecoinTotal` 把稳定币从 crypto 挪到 cash，总资产不变；快照（asset_snapshots）与历史曲线由该方法写入，自动跟随；底层数据不动（manual_assets.type 仍为 crypto，定投扣 USDT 与账户规则不受影响）。**历史快照不迁移**，曲线切换日（2026-10-30）有一次性分类跳变。资产历史页的分类展示顺序是前端固定序列 `CATEGORY_ORDER`，不遍历后端 Map 键序（后者随持仓市值排序漂移）。
     → TotalAssetSeriesService 按日期聚合 → ECharts
```

### 6.1 改代码前必须知道的五条

| 规则 | 内容 | 证据 |
|------|------|------|
| **物理级联删除** | 删持仓会物理删除交易、分红事件、定投计划、快照，**但不回退初始买入扣的现金** | `HoldingService.java:323-337` |
| **交易后重算** | 创建/编辑/删除交易后，先 `recalculateSharesFromScratch` 重算份额，再 `recalculateHoldingMetrics` 重算成本 | `TransactionService.java:186, 243` |
| **交易金额模式** | 前端卖出输入的是**总金额**，提交前折算 `perSharePrice = 总价 / 数量`；后端再算 `total = qty × price + fee`——这正是 P1-1 的根因 | `TradeAddPage.vue:205-210` |
| **快照三入口** | ① 定时 23:30（每 5 天）② `POST /api/asset-overview/snapshot` 手动 ③ 发现页首次加载自动 `takeSnapshot()`。三者都**覆盖当天**，靠 `@Modifying(flushAutomatically, clearAutomatically)` 保证 DELETE 先于 INSERT | `HoldingSnapshotRepository.java:25` |
| **分类入口唯一** | 新建持仓页**故意没有**分类字段，分类统一在发现页 / 持仓详情设置。未分类持仓不计入总资产，靠发现页横幅提醒 | `HoldingAddPage.vue`、`AssetOverviewService.java:52-57` |

## 七、算法口径

| 算法 | 公式 | 边界 |
|------|------|------|
| `diluted` 分红摊薄 | `(买入 − 卖出 − 累计分红) / 当前份额` | 可为负 → 息率返回 `-1`，前端显示「已收回」 |
| `diluted_only` 摊薄成本 | `(买入 − 卖出) / 当前份额` | — |
| `weighted_avg` 加权平均 | `买入 / 买入份额`，永不 < 0 | 卖出不影响成本 |
| 预测年分红 | 近 3 年单次均值 × 频率识别次数 × 份额 | 频率靠除权日间隔：25–35 / 80–100 / 330–400 天 |
| 成本息率 | 预测每股分红 / 每股成本 × 100% | 成本 ≤ 0 → `-1` |
| 回本年限 | `max(净投入 − 已收分红, 0) / 预测年分红` | 分红为 0 → `999`（魔法数） |
| IRR | 现金流按持有期归一化 → 二分求解 → `(1+r)^(365/days)−1` | 单笔、<7 天、成本 0、未收敛 → `null`；超出 [−95%, 1000%] → `abnormal` |

完整推导见 [参考/财务算法.md](参考/财务算法.md)、[参考/年化收益率IRR算法.md](参考/年化收益率IRR算法.md)。

**年化收益率三层保护**（`AnnualizedReturnService`）：

1. 持有 < 7 天 → 返回 `null`
2. IRR 100 次迭代后 `|NPV| > 0.01` → 返回 `null`（未收敛）
3. 年化结果超出 `[-95%, 1000%]` → 返回 `null`，标 `status=abnormal`

### 8.1 分红爬虫防伪规则（改爬虫前必读）

基金代码会被复用（`016452` 曾是其他基金，后被纳指100 复用），必须按成立日期过滤：

- **唯一过滤点**：`DividendTableProvider.isValidExDate` —— 仅 `exDate == null` 或 `exDate < 成立日期` 才丢弃。
- **不要用「未来日期」当脏数据判据**：已公告、除息日未到期的分红必须入库。2026-09-06 曾因此漏掉 021550 在 09-10 发放的分红（09-08 除息），日历不显示，后已移除该过滤。
- 分红记录被清空时，`DividendEventSyncService` 必须级联清理旧事件，否则脏事件残留。
- 历史事故：纳指100（016452）未按成立日过滤，产生 12 条假分红，导致息率异常。
