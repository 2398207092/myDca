### 2.1 本地开发陷阱（踩过的坑）

| 现象 | 原因 | 处理 |
|------|------|------|
| 启动报 `Unresolved compilation problems` | 改了 Repository 方法签名（如 `void` → `int`），增量编译沿用旧 `.class` | `mvn clean compile` 强制重编 |

| 复杂命令引号被吃掉 | PS 嵌套引号 | 写入 `.ps1` / `.bat`，用 `-File` 执行 |

## 三、部署

### 前端（自动）

```bash
git push origin main     # 触发 .github/workflows/deploy.yml
```

流程：`npm ci` → `npm run build` → scp `dist/` 到 `/www/wwwroot/fund-tracker/www/`（`rm: true`，**非原子**）→ 部署校验（属主必须 `admin`、6 个关键产物齐全、`manifest.json` 已指向新图标，任一不满足即 `exit 1`）。

> **末步不再是 `sudo aa_nginx -s reload`**（2026-10-30 改）。原因：reload 依赖 `/var/run/nginx.pid`，该文件在 tmpfs 上、重启即失，`-s reload` 恒报 `open() "/var/run/nginx.pid" failed` 并返回 1，导致「文件已上传成功但流水线标红」。前端静态文件由 nginx 直接读盘，本就不需要 reload。若确需重载配置，用 `sudo kill -HUP $(pgrep -o -f 'nginx: master')`。

> push 即上生产。**未获用户明确授权不得 push。**

**静态目录属主陷阱（2026-10-30 修复，务必保留本节）**

`www/` 必须由 `admin` 拥有。若属主是 `197609:197121`（Windows 的 UID），`admin` 在 755 下既不能删也不能写，Actions 的 `rm: true` 会在删除阶段被拒 —— 表现为 **push 成功、Actions 报红、线上毫无变化**。

成因：从 Windows 用 `tar` 打包 `dist/`，再到服务器 `sudo tar -x` 解压。`sudo` 有权限，会**忠实还原归档里的属主**，把 Windows UID 搬到服务器上。普通用户解压反而不会（tar 会忽略属主归给解压者）。

规则：

- 手动部署必须 `sudo tar xzf xxx.tar.gz -C <目标> --no-same-owner`，或干脆只走 Actions
- 每次部署后核对：`ls -ld /www/wwwroot/fund-tracker/www` 应显示 `admin admin`
- 属主异常一律 `sudo chown -R admin:admin /www/wwwroot/fund-tracker/www` 修复

**如何确认部署真的生效（不要只看 Actions 绿叉）**

```bash
curl -s -o /dev/null -w "%{content_type}\n" https://<域名>/icon-192.png
# 期望 image/png
# 返回 text/html ⇒ 命中了 SPA 兜底，该文件根本不存在（nginx 对缺失资源返回 index.html 且 HTTP 200）
```

> 2026-10-30 教训：8 个图标全部返回 `200`，但 body 都是 1537 字节的 index.html。只看状态码会被骗，必须看 `content_type` 或 `size_download`。

### 3.1 部署授权（AI 必守）

以下操作属于「生产端操作」，**必须先报告变更摘要，再等用户明确授权词**：

`git push` / `git commit` / `scp` 上传 / `ssh` 执行服务器命令 / `gh` 操作远程仓库。

| 视为授权 | 不视为授权 |
|---------|-----------|

### 3.2 版本更新 Runbook（2026-10-28 加密币+账户体系版本）

本轮变更：加密币定投/账户本位币约束/现金联动重构/定投适配。**前端 push 即上生产，后端手动**——顺序必须：数据库 DDL → 后端 JAR → 前端 push。

**① Schema 变更（上线前在服务器 MySQL 手动执行）**

`ddl-auto: update` 只加列、**不改已有列类型**——精度变更必须手动 ALTER，否则 BTC 定投份额继续被截断：

```sql
ALTER TABLE holdings MODIFY shares DECIMAL(24,8), MODIFY account_id VARCHAR(36) NULL;
ALTER TABLE dca_plans ADD COLUMN account_id VARCHAR(36) NULL;
ALTER TABLE transactions MODIFY quantity DECIMAL(24,8) NOT NULL, MODIFY price DECIMAL(24,8) NOT NULL;
-- manual_assets 的 asset_code/quantity/unit_price/price_source/price_updated_at 若生产库已有则跳过
```

**② 后端**：`mvn clean package -DskipTests` → scp → `./deploy.sh`（三、部署 节原流程）。启动后新列由 ddl-auto 补齐。

**③ 环境变量确认**（`override.conf`）：`DB_PASSWORD` / `APP_AUTH_TOKEN` / `APP_ADMIN_EMAIL` 照旧；**不得设置 `AUTH_QUICK_LOGIN`**（一键登录仅限本地）。

**④ 数据迁移（BTC 从 manual_assets 迁入 holdings）**：与本地 10/27 流程相同——生产库 BTC 是 manual_assets（数量/成本见该行），迁移要点：建仓不生成带手续费的买入交易、`cost_estimated=1`、`quote_currency='USDT'`、`account_id`=USDT 账户、迁移后原 manual_assets 行改名「BTC（已迁入）」保留。**迁移后手动补一条 10/27 的 holding_snapshot 作为涨跌基准（值=迁入市值），否则周涨跌显示「暂无」**。

**⑤ 验证清单**：`/api/asset-overview` 总资产与分项一致；BTC 详情页成本/现价口径为 USDT+人民币双显；基金定投执行后日常账户现金减少（确认单扣不双扣）；登录页**无**一键登录按钮。

**⑥ 回滚**：`deploy.sh` 的 `.bak` JAR 回退 + `git revert` 前端；数据回滚用每日 10:00 的 mysqldump 备份（GitHub Actions db-backup.yml）。

### 4.1 安全加固基线（不得削弱）

| 项 | 配置 | 说明 |
|----|------|------|
| MySQL | `bind-address = 127.0.0.1`、`mysqlx = OFF` | 禁外网 3306 / 33060；应用账号 `fundapp` 仅授权 `fund_tracker.*` |
| firewalld | 仅开 `22` / `80` / `443` | 封 `3306` `8080` `8888` `33060` |
| SSH | `PermitRootLogin no` + 密钥优先 + fail2ban（10 分钟 5 次失败封 IP） | — |
| systemd | 环境变量放 `override.conf`，权限 `600` | 路径 `/etc/systemd/system/fund-tracker.service.d/override.conf`，改后 `daemon-reload` + `restart` |
| 数据库客户端 | 禁止外网直连 3306 | Workbench 走 SSH 隧道：SSH `:22` → MySQL `127.0.0.1:3306` |
| JVM | `-Xmx384m -Xms256m`（`pom.xml:126`） | **仅对 `mvn spring-boot:run` 生效**；生产 `java -jar` 的实际堆参数需在 systemd 里确认 |

## 十、安全更新与回滚方案（2026-10-28 定稿）

三个原则：**测试与生产物理隔离**、**Schema 只做向后兼容变更**、**回滚预案预写不现场想**。

### 10.1 测试 / 生产隔离

| 层 | 测试环境 | 生产环境 | 隔离手段 |
|----|---------|---------|---------|
| 代码 | `dev` 分支 | `main` 分支 | deploy.yml 仅 `main` 触发（已确认 `.github/workflows/deploy.yml:5`），push dev 不上生产 |
| 数据库 | 本地 `fund_tracker`（可随意造数） | 服务器 `fund_tracker` | **禁止任何方向把本地表直接灌进服务器**；反向（生产→本地做测试）允许 |
| 验证 | 上线前用生产备份在本地起一个 `fund_tracker_prod_test` 库，跑新版本代码做全功能冒烟 | 真实数据 | 库名不同，永不混淆 |

- 任何「从本地导数据到服务器」的操作都是红线——2026-10-27/28 两轮测试数据污染（BTC 快照、asset_snapshots 脏行）若发生在生产即事故。
- 后端启动日志打印当前环境（生产 systemd 配置 `APP_ENV=prod`），登录页应**无**「一键登录」按钮，作为目视检查项。

### 10.2 更新流程（七步）

前提原则：**Schema 变更必须向后兼容**——只加列（nullable）、只加宽精度（18,4→24,8）；不改列名、不删列、不收窄。历史数据在新版本由旧列+旧值自然展示，新列空值由界面显示「未归属/未分类」兜底，不报错。

| 步 | 动作 | 要点 |
|----|------|------|
| 1 | dev 分支完成开发，本地全量测试（`mvn test` + `vue-tsc` + `check-all.sh`） | 绿了才进下一步 |
| 2 | **生产备份三件套**：`mysqldump` 全量 + `fund-tracker.jar` 拷贝 + `dist/` 前端产物拷贝，存 `/home/admin/backup/YYYYMMDD/` | 每次更新都做，不等每日定时 |
| 3 | 生产库执行 DDL 清单（见 3.2 节本轮 4 条） | root 执行；加宽精度对旧数据无损，新列 nullable |
| 4 | 后端部署：`mvn clean package` → scp → `./deploy.sh`（自带 `.bak`） | 先码后前端 |
| 5 | **验证清单**（见 3.2 节⑥）：总资产分项、历史曲线、分红记录、定投执行、登录页无一键登录 | 历史数据显示是必查项 |
| 6 | 前端：dev merge 到 main → push（Actions 自动上生产） | 最后一步，失败可单独 revert |
| 7 | 生产数据迁移（如 BTC 迁 holdings）：**界面手动操作**，不跑脚本 | 每步截图，出错可撤销 |

### 10.3 回滚机制（三层）

| 层 | 触发条件 | 操作 | 耗时 | 数据影响 |
|----|---------|------|------|---------|
| **L1 程序回滚** | 新版启动失败 / 接口 5xx / 页面崩溃，数据无损坏 | 后端：`mv fund-tracker.jar.bak fund-tracker.jar && systemctl restart fund-tracker`；前端：`git revert` + push，或把备份 `dist/` 原样拷回 | 2-5 分钟 | 无（旧代码读新列多余字段无害，无需动库） |
| **L2 Schema 回滚** | 仅当 L1 后仍因 DDL 引发问题（罕见） | 新列 `DROP COLUMN`；精度回窄**必须先查截断风险**：`SELECT COUNT(*) FROM transactions WHERE quantity <> TRUNCATE(quantity,4)`（有行则禁止回窄，先导出） | 10 分钟 | 新列当天数据丢失（可接受）；精度回窄可能截断——默认不做 |
| **L3 数据回滚** | 数据被错误写入/损坏（如快照污染） | 优先**单表恢复**（`mysqldump` 备份中的对应表）；全量恢复前**必须先把当前状态再 dump 一份**留档，因为全量恢复会抹掉备份之后的真实操作（用户新增存款等） | 30 分钟 | 恢复点之后的真实录入需要重做 |

**回滚预案三脚本预写在服务器 `/home/admin/rollback/`**：`rollback-jar.sh`（L1）、`rollback-ddl.sql`（L2）、`restore-db.sh`（L3，带恢复前二次 dump）。出事按序号执行，不现场想命令。

### 10.4 首道防线（比回滚更重要）

1. 生产库应用账号 `fundapp` 仅授权 `fund_tracker.*`（已配）——DDL 永远走 root 手动执行且先备份。
2. 禁止从本地向服务器导数据（10.1 红线）。
3. 测试子代理/自动化**不得直连生产**；涉及生产的验证一律走「生产备份恢复到本地」路径。
4. 每日定时备份（db-backup.yml，北京 10:00，保留 30 天）+ 每次更新前的手动三件套备份。
5. 部署授权规则见 3.1 节——AI 不经明确授权词不 push、不部署。
