## 一、当前是怎么工作的

分红数据**不是从 API 拿的，是爬 HTML 表格爬来的**。整条链路五步：

```
① 取成立日期   fundmobapi.eastmoney.com/FundMNewApi/FundMNBasicInformation
              UA 必须用 curl/8.0（浏览器 UA 会被反爬）
              → 正则提取 ESTABDATE → 内存缓存（静态属性，抓一次永久用）
                     ↓
② 抓分红页     fundf10.eastmoney.com/fhsp_{code}.html
              UA 用浏览器 UA
              → Jsoup 定位表格 → <tr>/<td> 逐行解析
              → 取 cells[3]「每10份分红」，含"每10份"则 ÷10 折算为每份
                     ↓
③ 脏数据过滤   除权日 < 基金成立日期 → 丢弃
              （防基金代码被复用后，抓到前一只基金的分红）
              成立日期获取失败时，退化为 FALLBACK_MIN_EX_DATE = 2020-01-01
                     ↓
④ 增量入库     existsByFundCodeAndExDate 去重，source 字段写死 "scrape"
                     ↓
⑤ 联动         syncAllEvents() 同步到日历事件
              → refreshAllHoldings() 刷新预测分红、已收分红
```

**触发入口三处**：

| 入口 | 位置 | 时机 |
|------|------|------|
| 定时批量 | `scheduler/FundDividendScheduler.java:35` | 每天 06:00 `0 0 6 * * ?` |
| 手动触发 | `controller/FundDividendController.java:32` | 调接口时 |
| 添加持仓 | `service/HoldingService.java:192`、`:508` | 新建/刷新持仓时 |

**关键文件**：

| 文件 | 职责 |
|------|------|
| `service/provider/EstablishDateProvider.java` | 成立日期（curl/ UA） |
| `service/provider/DividendTableProvider.java` | 分红页抓取 + HTML 表格解析 |
| `service/FundDividendScrapeService.java` | 流程编排、分页循环、增量入库、年化计算 |
| `service/DividendInfoService.java` | 分红口径选择（ex_date / report_period） |
| `service/DividendEventSyncService.java` | 分红记录 → 日历事件 |
| `scheduler/DividendAutoDistributeScheduler.java:33` | 每天 09:30 自动派发 |

所有结论均有真实请求支撑，可复现。

## 三、问题清单

### #1 分红表选择器三层已死两层 🔴 高

- **问题类别**：外部页面结构耦合 / 静默失效
- **严重程度**：🔴高
- **文件**：`service/provider/DividendTableProvider.java:85-91`
- **大白话**：程序靠"表格长什么样"来认目标表，给了三条认法。实测下来**前两条已经完全认不出来了，现在全靠最后一条勉强认出来**。哪天网站把"权益登记日"这四个字改一下，分红数据就会悄悄停止更新，你在界面上完全看不出来，只有日志里留一行"未找到分红表格"。

现有三层选择器实测结果：

| 顺序 | 选择器 | 实测命中 | 说明 |
|------|--------|---------|------|
| 1 | `table.w782.comm.jjfl` | **0 次** | class 名已变，现在是 `cfxq` |
| 2 | `table:has(th:contains(每份分红))` | **0 次** | 表头写的是「每**10**份分红」，中间夹了数字，字符串不匹配 |
| 3 | `table:has(th:contains(权益登记日))` | 1 次 | **唯一生效的一条** |

- **风险量级**：目前功能正常，属于「能用但悬在空中」。一旦失效，后果是**分红数据静默停更**——不会报错、不会告警，只是数据库不再增长。对分红追踪类应用这是核心功能失效。
- **修复方案**：
  - 首选按 `class='w782 comm cfxq'` 精确匹配（当前真实结构），并把 `jjfl` 作为历史兼容保留
  - 保留「权益登记日」文本兜底，但增加**解析结果为空时的告警**——`scrapeAndSave` 当前遇到空列表只打 `log.info`，应升级为 warn 并计入 `MonitorLogService`
  - 长期：`ExternalApiProbeTest` 里已有分红页探针（检查 `派现金` / `每份分红`），建议把「表格命中数」也纳入断言

### #2 分页循环空转，反复请求同一批数据 🟡 中

- **问题类别**：无效外部请求 / 反爬风险
- **严重程度**：🟡中
- **文件**：`service/FundDividendScrapeService.java:75-100`
- **大白话**：程序以为这张表有很多页，翻完第 2 页翻第 3 页。但实测网站根本不支持翻页，每页返回的都是同一张完整的表。结果**分红记录超过 20 条的基金，每抓一次会发 10 个请求，其中 9 个拿到的是一模一样的数据**。

代码逻辑：

```java
int page = 1;
while (hasMore && page <= 10) {
    List<FundDividendRecord> pageRecords = dividendTableProvider.fetchDividendRecords(...);
    if (pageRecords.isEmpty()) break;
    ...
    hasMore = pageRecords.size() >= 20;   // 37 >= 20 → true，一直循环
    page++;
}
```

实测后果推演（以 007466 的 37 条为例）：

| page | 请求 | 拿到 | 新增 | hasMore |
|------|------|------|------|---------|
| 1 | 有效 | 37 条 | 37 条 | true |
| 2~10 | **全部重复** | 37 条 | 0 条 | true |
| 退出 | — | — | — | page > 10 |

→ **共 10 次请求，有效 1 次，浪费 9 次**。配合 `scrapeMultiple` 里每只基金间隔 `Thread.sleep(500)`，持仓中若有多只高分红基金，每天 06:00 的定时任务会成倍放大请求量。

- **风险量级**：当前不会导致数据错误，只会浪费请求与时间，并提高被天天基金识别为异常流量的概率。属于「不修也能跑，但没理由留着」。
- **修复方案**（改动最小的方案）：
  - 既然页面不分页，直接把循环改为单次抓取：删掉 `while`，只保留一次 `fetchDividendRecords(fundCode, establishDate, 1)`
  - 若为将来分页恢复留余地，则改为：**按原始行数判断**（见 #3），并在连续两次拿到相同首条记录时提前 break

### #3 `hasMore` 用过滤后的数量判断，存在漏页隐患 🟡 中

- **问题类别**：逻辑错误（潜在数据缺失）
- **严重程度**：🟡中
- **文件**：`service/FundDividendScrapeService.java:98`
- **大白话**：决定"要不要继续翻页"时，程序数的是**过滤之后的条数**。过滤会把成立日期之前的记录剔掉。如果一只老基金本来一页有 20 条，被剔掉 5 条只剩 15 条，程序就会以为"这页没满，后面没数据了"，直接停下——**后面页的数据就漏了**。

```java
// pageRecords 已经过 isValidExDate 过滤（剔除成立日期前的脏数据）
hasMore = pageRecords.size() >= 20;   // 应该用解析出的原始行数
```

- **风险量级**：当前因为 #2 所述「页面根本不分页」而未实际爆发。一旦天天基金恢复真分页，这个问题会直接导致**历史分红记录缺失**，且无任何报错。
- **修复方案**：让 `DividendTableProvider` 同时返回「原始解析行数」与「过滤后记录」，`hasMore` 用原始行数判断。

### #4 `report_period` 口径把净值增长当成分红 ⚪ 低（但会误导）

- **问题类别**：计算口径失真
- **严重程度**：⚪低（默认不走，但结果会明显偏大）
- **文件**：`service/DividendInfoService.java:76-97`、`:146-179`
- **大白话**：除了"按实际分红加总"这条准的算法，还有一条路是"看累计净值涨了多少，倒推分红"。问题是**净值涨了不等于分红**——基金涨的那部分是收益，不是发给你的现金。这条路算出来的数字会明显偏大。

```java
private BigDecimal calcByReportPeriod(String js, long cutoffMs, String horizon) {
    // 取时间段首尾 Data_ACWorthTrend 累计净值差 ÷ 年数
    BigDecimal diff = endRec.accNav.subtract(startRec.accNav);
    return diff.divide(BigDecimal.valueOf(years), 4, RoundingMode.HALF_UP);
}
```

- **风险量级**：默认 `method=ex_date`，不触发。只有前端显式传 `method=report_period` 时才走这条路，此时年化分红数字会偏大（把净值涨幅算进去了）。
- **修复方案**：建议直接下线该口径，或在前端加明确标注「此口径含净值增长，非纯分红」。代码里已有一段兜底逻辑（report_period 失败后回落 fhsp），说明作者本人也不完全信任它。

## 四、修复优先级建议

| 优先级 | 问题 | 改动量 | 理由 |
|--------|------|--------|------|
| 1 | #2 分页空转 | 删一个 while 循环 | 改动最小、收益直接，消除 9/10 的无用请求 |
| 2 | #1 选择器加固 | 改选择器 + 加告警 | 保护核心功能，防止静默停更 |
| 3 | #3 hasMore 判断 | 改一个判断依据 | 顺手一起改，避免将来踩坑 |
| 4 | #4 口径下线 | 删代码 / 加标注 | 不影响主流程，但能消除一个数据失真源 |

**关联建议**：`DividendTableProvider` 与 `FundDividendScrapeService` 都应增加「解析结果为空」的告警上报到 `MonitorLogService`。当前静默失败是这条链路最大的隐患——数据停了但界面上看不出来。

## 五、关联记录：净值链路的两个已知问题

审计分红时顺带发现，未展开验证，仅登记待办：

1. **`FundNavScrapeService.java:44` 注释与实现不符** —— 注释写「最近 5 年」，代码 `oneYearAgo` 实际只存**最近 1 年**。首次建档时 2025 年之前的历史净值不会入库。
2. **`fetchPingZhongDataWithRetry(fundCode, 15000)` 的 `timeoutMs` 是死参数** —— 传入后未被 `NavDataProvider.fetchRawJs(fundCode)` 使用，实际固定 10s。

净值数据源本身的实测结论（供参考）：`pingzhongdata/{code}.js` 可用（280 KB / 3457 个净值点 / 覆盖成立至今），但**无任何 fallback 数据源**。已实测可用的备用源包括蛋卷 `danjuanfunds.com/djapi/fund/nav/history/{code}`（标准 JSON）与天天基金移动端 `FundMNHisNetList`（标准 JSON）。
